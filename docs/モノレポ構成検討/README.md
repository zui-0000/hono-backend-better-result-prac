# モノレポ構成検討

次に作るリポジトリ（React + Hono のフルスタック TypeScript）をどう組むか。
**このリポジトリには実装を入れない。** 決めたこと、見送ったこと、その理由だけを置く。

| 読むもの                                    | いつ                                                         |
| ------------------------------------------- | ------------------------------------------------------------ |
| **[API 層の選定](API-層の選定.md)**         | **FE と BE をどう繋ぐか。oRPC を選んだ理由と、その代償**     |
| [ビルドツールの選定](ビルドツールの選定.md) | Vite+ を見送った理由。同梱ツールチェーンが何と引き換えか     |
| [リポジトリ構成](リポジトリ構成.md)         | ディレクトリ、catalog と `workspace:` の使い分け、未決の項目 |

> **調査日: 2026-08-21。** 記載のバージョンは全て当日の npm / GitHub 実測値。
> 候補がどれも動きの速い依存なので、**着手時に必ず取り直すこと**。数字を信用しない。

---

## 決めたこと

| 項目             | 採用                       | 理由の要点                                  |
| ---------------- | -------------------------- | ------------------------------------------- |
| API 層           | **oRPC** (v1 系)           | 契約を型で強制でき、OpenAPI も出せる        |
| パッケージ管理   | **pnpm workspace**         | 既に使っている。catalog がある              |
| バージョン一元化 | **pnpm catalog**           | ロックステップな依存群を 1 箇所に固定できる |
| パッケージ間参照 | **`workspace:*`**          | レジストリを見に行かせない                  |
| BE の実行        | ランタイム直実行 or tsdown | Vite にビルドさせる必然性が無い             |

## 見送ったこと

| 候補         | 見送った理由                                                                   |
| ------------ | ------------------------------------------------------------------------------ |
| **Vite+**    | oxlint / oxfmt のバージョン主導権を失う。詳細は[こちら](ビルドツールの選定.md) |
| **tRPC**     | OpenAPI が出せない。将来 TS 以外のクライアントが来ると詰む                     |
| **Hono RPC** | ルート数が増えると型推論が重い。OpenAPI は結局別建て                           |
| **ts-rest**  | 思想は近いが、開発の勢いが oRPC に劣る                                         |
| **oRPC v2**  | 2026-08 時点で beta。安定版が出てから移行する                                  |

---

## このリポジトリとの一番の違い

**契約の source of truth が、TypeSpec から TypeScript に移る。**

|            | このリポジトリ                    | 次のリポジトリ                     |
| ---------- | --------------------------------- | ---------------------------------- |
| 正         | `schema/`（TypeSpec）             | `packages/contract`（TypeScript）  |
| OpenAPI    | **入力**。ここから zod を生成する | **出力**。コードから吐かれる成果物 |
| 性格       | prescriptive（規定）              | descriptive（記述）                |
| コード生成 | 要る（orval）                     | **要らない**                       |

これは優劣ではなく、**軸の反対側に移る**という話。

言語中立の IDL を正に置く重さと、TS に直結させる軽さ。両方を実際に組んで、
どちらがどこで効くかを身体で知るのが目的。**片方しか知らないと選べない。**

> 注意: この移動によって「片方だけ直すと静かにズレる」の発生箇所も変わる。
> このリポジトリでは契約とドメインの二重管理がそれだった（[CLAUDE.md の「契約」](../../CLAUDE.md)）。
> oRPC では契約と実装が型で結ばれるのでそこは消えるが、**代わりに OpenAPI が
> コードに追従するだけの存在になる**。仕様書として読ませたいなら別の担保が要る。
