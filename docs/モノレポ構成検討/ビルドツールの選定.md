# ビルドツールの選定 — Vite+ を見送った

[README](README.md) の補足。**結論から言うと採用しない。**
ただし惜しい選択肢だったので、何と引き換えだったかを残す。

---

## 1. Vite+ とは何だったか

VoidZero の統合ツールチェーン。Vite / Vitest / Oxlint / Oxfmt / Rolldown / tsdown /
タスクランナーを **`vp` という 1 つのバイナリ**にまとめたもの。

発表時は「大きい組織は商用」だったが、**2026 年 3 月に MIT で完全オープンソース化**された。
つまりライセンスは検討材料ではなくなっている。

|                 | 2026-08-21 実測                       |
| --------------- | ------------------------------------- |
| npm `vite-plus` | **0.2.9**（2026-08-12）               |
| リポジトリ      | `voidzero-dev/vite-plus` ★5,615 / MIT |
| バイナリ        | `vp` / `vpr`（= `vp run`）            |

---

## 2. 惹かれた理由

**設定ファイルが 1 枚に畳めること。** これに尽きる。

このリポジトリは今こうなっている。

```text
.oxlintrc.jsonc          20KB
.oxfmtrc.jsonc
.dependency-cruiser.mjs
orval.config.ts
```

Vite+ なら lint / fmt / test / タスク定義 / キャッシュが `vite.config.ts` 1 枚に乗る。
モノレポでパッケージごとに上書きもできる。

```ts
lint: {
  plugins: ['typescript'],
  overrides: [{ files: ['apps/frontend/**'], plugins: ['react'] }],
},
```

**設定を 3 箇所にコピペして静かにズレる、が起きない。** これは魅力だった。

タスクランナーも素性が良い。`vp run` は `package.json` の依存グラフから順序を組み、
入力ファイルと環境変数を自動でフィンガープリントしてキャッシュする
（Turborepo の `inputs` / `outputs` 手書きが要らない）。

---

## 3. 見送った理由

### 3-1. oxlint / oxfmt のバージョン主導権を失う（決め手）

`vite-plus@0.2.9` の依存を実際に見るとこうなっている。

```text
oxlint:  =1.77.0    ← 完全固定
oxfmt:   =0.62.0    ← 完全固定
vitest:   4.1.10    ← 完全固定
```

**このリポジトリは既に oxlint `^1.78.0` / oxfmt `^0.63.0`。Vite+ より新しい。**

Vite+ に乗るということは、**lint と formatter の更新を `vite-plus` のリリース
サイクルに預ける**ということ。20KB の `.oxlintrc.jsonc` を育てている立場で、
ここの主導権を手放す判断は割に合わない。

**これが「同梱ツールチェーン」の本質的な対価。**
設定が 1 枚になる代わりに、構成要素を個別に最新へ追えなくなる。

### 3-2. catalog を使うなら踏む地雷がある

`vp create` / `vp migrate` が吐く `pnpm-workspace.yaml` はこうなる。

```yaml
catalog:
  vite: npm:@voidzero-dev/vite-plus-core@0.2.9 # ← エイリアス
  vite-plus: 0.2.9
```

**この 2 行は常に同じバージョンで動かないと壊れる。**
ところが Renovate / Dependabot から見れば `vite-plus` と
`@voidzero-dev/vite-plus-core` は赤の他人なので、**1 回のリリースが 2 本の
独立した PR に割れる**。

> 結果、`vite-plus` 0.2.9 × core 0.2.1 という**リリースされたことのない
> 組み合わせ**で CI が走り、それが緑になる。

公式リポジトリで 1 ヶ月放置された実例が
[voidzero-dev/vite-plus#2356](https://github.com/voidzero-dev/vite-plus/issues/2356)
に記録されている。**`vp migrate` が作る全リポジトリがこの形。**

`vitest` も同じ。`vp` がバンドル版に override でピン留めしているので、
単独で上がると同様に壊れる。

回避は可能（Renovate のグループルール）だが、**何もしないと壊れることに気づけない**
種類の問題で、しかも各リポジトリが個別に再発見する必要がある。

### 3-3. まだ 0.x

2 週間おきにマイナーが出ている。破壊的変更は来る前提。
これ単体なら学習リポジトリでは許容範囲だが、3-1 と重なると天秤が傾いた。

## 4. 誤解しないための注記

見送った理由に**入っていない**ものを明記しておく。後で読み返したときに
理由を取り違えないため。

| よくある懸念              | 実際                                                                                  |
| ------------------------- | ------------------------------------------------------------------------------------- |
| モノレポで動かないのでは  | **動く。看板機能。** `vp run` は Turborepo 相当                                       |
| pnpm catalog に非対応では | **対応済み。** `vp add --save-catalog` / `--save-catalog-name`、`catalogMode: prefer` |
| 有料では                  | **無料。** 2026-03 に MIT 化                                                          |

catalog 対応については、issue [#1835](https://github.com/voidzero-dev/vite-plus/issues/1835)
が open のまま残っているが、**中身は「どのカタログに入れるか対話 TUI で選ばせて」
という UX 要望**であって、機能が無いわけではない（メンテナが回答済み）。
`vp up` が `catalog:` 参照を壊す不具合も 2026-08 に修正されている。

**issue が open であることと、機能が無いことは違う。** タイトルだけで判断しない。

## 5. では何を使うか — **未決**

### いまの想定

パッケージが 3 つ（`contract` / `frontend` / `backend`）の規模なら、
**素の pnpm で足りる**。

```bash
pnpm -r build
pnpm --filter @app/frontend dev
pnpm --filter "...@app/contract" test   # contract に依存する側も含める
```

ツールは個別に持つ。今のリポジトリと同じ形で、バージョンも自分で握る。

### Turborepo を足す引き金

- `pnpm -r build` の待ち時間が体感で気になり始めたとき
- CI でビルド結果をキャッシュしたくなったとき

**先回りで入れない。** キャッシュが要る規模になってから足す。

### Vite+ を再検討する引き金

- **oxlint / oxfmt のバージョンを Vite+ が追い越したとき**（3-1 が解消する）
- 1.0 が出たとき
- 公式の Renovate プリセットが用意されたとき（[#2356](https://github.com/voidzero-dev/vite-plus/issues/2356) の案 1）
  か、バージョン skew を `vp` が検出して落とすようになったとき（同案 2）

**思想は良い。時期の問題。**
