# リポジトリ構成

[README](README.md) の補足。ディレクトリと、依存の張り方を決める。

---

## 1. ディレクトリ

```text
pnpm-workspace.yaml
packages/
  contract/          ← @orpc/contract。契約はここだけ
apps/
  frontend/          ← React + Vite
  backend/           ← Hono + oRPC
```

**`packages/contract` が唯一の結節点。** frontend と backend は互いを知らず、
両方が contract だけを見る。

```text
frontend ──┐
           ├──> contract
backend  ──┘
```

この形が崩れる（frontend が backend を直接参照する等）と、モノレポにした意味が消える。
**このリポジトリで dependency-cruiser に守らせている構造規律の、パッケージ版。**
同じ道具で守れるかは[未決](#5-未決の項目)。

## 2. 依存の張り方 — 2 通りある

| 書き方             | 何のため                                    | 例                      |
| ------------------ | ------------------------------------------- | ----------------------- |
| **`workspace:*`**  | **同じリポジトリの中を指す**                | `"@app/contract"`       |
| **`catalog:<名>`** | **外部依存のバージョンを 1 箇所に集約する** | `"react"` / `"@orpc/*"` |

混同しやすいが、**解決する問題が別**。前者は「どこを見るか」、後者は「どの版か」。

### pnpm-workspace.yaml

```yaml
packages:
  - "apps/*"
  - "packages/*"

catalogMode: prefer # 素の `pnpm add` が既定でカタログを見る

catalogs:
  shared: # 3 パッケージ全部が使う
    zod: ^4.4.3
    "@orpc/contract": ^1.15.0
  frontend:
    react: ^19.2.8
    react-dom: ^19.2.8
    "@tanstack/react-query": ^5.101.4
    "@orpc/client": ^1.15.0
    "@orpc/tanstack-query": ^1.15.0
  backend:
    hono: ^4.13.3
    "@orpc/server": ^1.15.0
```

### 各パッケージの package.json

```jsonc
// apps/frontend/package.json
"dependencies": {
  "@app/contract": "workspace:*",   // ← リポジトリ内。レジストリを見に行かない
  "react": "catalog:frontend",      // ← 版は workspace 側が持つ
  "zod": "catalog:shared"
}
```

## 3. なぜ catalog を使うか

**`@orpc/*` がロックステップだから。** `@orpc/contract` だけ上がって
`@orpc/server` が古いままだと壊れる。

3 パッケージそれぞれの `package.json` に `^1.15.0` を手書きすると、
**片方だけ上がって静かにズレる**。このリポジトリの
[「リフレッシュ券の寿命が 2 箇所に手書きされている」](../TODO.md)と同じ構図。

catalog は**その重複そのものを消す道具**。版が書いてある場所が 1 つしかないので、
ズレようがない。

> `catalogs:`（複数形・名前付き）を使い、`catalog:`（単数・既定）は使わない。
> 用途ごとに束を分けたほうが、どのパッケージが何を使うかが workspace ファイルだけで読める。

## 4. BE をどう建てるか

Hono のバックエンドは **Vite でビルドする必然性が無い**。選択肢は 3 つ。

| 案                    | 中身                                                            | 向く場面                                                 |
| --------------------- | --------------------------------------------------------------- | -------------------------------------------------------- |
| **A. バンドルしない** | ランタイムで TS を直接実行（今のリポジトリと同じ）              | **最も単純。開発中はこれ**                               |
| **B. tsdown**         | 1 ファイルに束ねる。dts / esm+cjs / minify / sourcemap          | **Docker や Lambda に投げるなら本命**                    |
| C. `@hono/vite-build` | Hono を Vite のビルドに乗せる（dev は `@hono/vite-dev-server`） | Vite のプラグインを**サーバ側でも**共有したいとき / edge |

**A で始めて、デプロイ先が決まったら B を足す。**
C は Vite プラグインを BE でも使う明確な理由が無い限り、レイヤーが増えるだけ。

参考バージョン（2026-08-21 実測）: `tsdown` 0.22.14 /
`@hono/vite-build` 1.11.1 / `@hono/vite-dev-server` 0.26.1。

## 5. 未決の項目

着手前に決めること。**決めてからでないと後で効かない**ものを上に置く。

### 5-1. パッケージ間の依存方向を何で守るか

`packages/contract` がサーバのコードを import したら壊れる、という規律を
**機械で守りたい**。候補:

- dependency-cruiser を**リポジトリ全体に対して**掛ける（今の資産が使える）
- `packages/contract` の `package.json` の `dependencies` を最小に保つだけで済ませる

**後から入れると既に違反が溜まっている**ので、最初に決める。

### 5-2. タスクランナーをいつ足すか

素の `pnpm -r` で始める。引き金は
[ビルドツールの選定 §5](ビルドツールの選定.md#5-では何を使うか--未決) に書いた。

### 5-3. 認証をどこに置くか

better-auth を使う想定。oRPC が Hono のルーティングを使わない
（[API 層の選定 §3-3](API-層の選定.md#3-3-hono-とは統合ではなく同居)）ため、
**認証は oRPC の middleware 側に寄せることになる**。

better-auth 自体は Hono に自分のルートを生やすので、そこは別系統で共存する。
**具体的な繋ぎ方は未調査。**

### 5-4. OpenAPI をどう扱うか

oRPC では OpenAPI が出力になる。**吐いた spec を何に使うか**を決めていない。

- ドキュメント表示だけ（Scalar 等）で済ませるのか
- CI で差分を検出して、契約変更を明示的にレビューさせるのか

後者をやるなら、**spec をリポジトリにコミットする必要がある**。
この判断が[README の「prescriptive → descriptive」](README.md#このリポジトリとの一番の違い)
の実務上の落とし所になる。
